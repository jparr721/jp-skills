# Startup V6 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Implement canonical Startup inboxes, persistent employee loops, additive hiring, and assigned monitoring on OMP, with the approved prompt-only fallback elsewhere.

**Architecture:** A companion extension wraps native task dispatch and owns one transactional SQLite store per bound Startup. Every distinct intake call fields a fresh architect-led QA/architect/dev team; the manager handles only requests, staffing, high-level decisions and reports. Native OMP turns remain bounded; logical employment survives yield, idle, parking, and restart. Existing queue files remain the canonical work source.

**Tech Stack:** TypeScript, Bun, SQLite, the installed OMP 18.8.9 extension interface, existing Markdown skills. Pin runtime/type dependencies after checking the installed interface.

**Spec:** `docs/superpowers/specs/2026-10-13-startup-v6-design.md`

## Global Constraints

- Stage 0 is a hard gate: stop dependent implementation if native feasibility fails.
- Keep OMP as execution authority; preserve native task policy, admission, isolation, budgets, transcripts, and root observability.
- Load complete canonical role and shared loop sources; assignments and source-tagged overrides are separate data.
- `hire devops 6` adds six more identities. Retry of the same request adds zero; another deliberate request adds six.
- Prefer hiring and immediate dispatch for ready independent work. Maximize parallelism within actual native capacity, budgets, dependencies, target grants, and explicit user limits; durable intake precedes dispatch.
- Intake capture is not a batch-completion barrier. Dispatch ready independent teams during other items' lookup/clarification/execution; before manager wait/standby/final, dispatch all work with free capacity or record its real blocker.
- Every distinct intake call creates a fresh team with exactly one QA, one architect leader, and one or more devs. Retry of the same event returns the original team. The manager ALWAYS delegates intake, never performs it. Architect handles technical detail, runs the sub-team, and reports only to the manager; members report through their architect. Shared DevOps scales up/down through the manager.
- Bind caller, Startup, manager root, owner epoch, and native generation from runtime evidence, never caller-supplied identity fields.
- Save cues before wake. Settle result, incoming acknowledgement, and outgoing manager messages atomically.
- Preserve V5 queue rows, IDs, unknown fields, receipts, resource inventory, history, and ambiguous locks.
- Every managed persona follows the loop, including manager, dev, DevOps, QA, architect, and PA. Queue drain means waiting, not retirement.
- Only the user or bound manager hires; other employees request capacity through the manager. Exactly one manager.
- Monitor targets, probes, cadence, acceptance, and repair authority come from manager assignment. Hire grants no mutation authority.
- Use managed timers; host exit means offline. Never claim observations during downtime.
- Outside a positively identified OMP session use verbatim canonical role prompts through supported subagent tools; recommend Oh My Pi once. Prompt-only mode supplies no runtime persistence guarantee.
- Startup boot creates or refreshes `<bound_root>/AGENTS.md` beside `.startup/`, preserves existing instructions, and includes explicit canonical skill/runtime guidance.
- ASCII-only new content. Strict boundary validation, explicit errors, functional modules, no invented OMP API or separate runner.
- Work only in this worktree. No publish, shared-branch push, live deployment mutation, normal-profile installation, or changes to unrelated Startup state.
- Required native feasibility and behavioral acceptance checks are part of this spec's implementation; use isolated fixtures and focused verification.

## Review Focus

- Lost hire response or partial launch retains original IDs and actual readiness.
- Stale generation or superseded host cannot acknowledge mail or mutate a target.
- Missing/changed role source blocks admission, including revived and synthetic turns.
- Restart coalesces missed read-only polls and retains uncertain mutations for reconciliation.
- Non-OMP and unknown harnesses select explicit prompt-only mode even when `omp` is installed.
