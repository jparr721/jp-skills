# Startup role dispatch

## Active harness

Use actual running OMP metadata and verified companion readiness. In other/unknown harnesses bind complete canonical role plus loop verbatim through supported subagent tools, with separate task data; notify once: "Oh My Pi is best-suited for this system." Prompt-only mode has no runtime persistence/monitoring guarantee. Known OMP with absent/failed companion is blocked until installed/booted; never silently downgrade or select OMP from an installed binary.

## Binding

1. Load the entire `skills/startup-role-<assigned-role>/SKILL.md` and `skills/startup-loop/SKILL.md` from the canonical repository. The root manager loads its manager role; a child loads its assigned role. A named skill, discoverable profile, summary, or self-report does not prove loading.
2. Native generated profiles and actual provider projection use those exact source texts and hashes. Record real source paths/revisions, native identity/generation, assignment and readiness receipt. Missing/changed sources block admission until supported reconciliation/refresh; an old handle is not source readiness.
3. Keep request, acceptance, repo/base, kind/procedure, authorization and source-tagged overrides in assignment data. Preserve persona authority. Overrides apply only to their named item/repo; resolve global standing instructions, selected config preferences, then repo/role guidance without granting new authority.
4. Record canonical role/procedure ID, source path, actual binding mechanism/handle, UTC time, result or concrete blocker in the ledger. Use `native-role`, `native-skill-preload`, or `verbatim-role-instructions` only when demonstrated by that dispatch.

## Routing

| Work | Binding and route |
| --- | --- |
| Human contact, team capacity, authorization, landing | Current `startup-role-manager` |
| Each distinct intake event | Fresh complete team; `startup-role-architect` runs full `startup-intake`, leads devs/QA, reports only to manager |
| Item execution | `startup-role-dev`, assigned kind/procedure; reports to own architect |
| Required item proof | Own `startup-role-qa`; reports to architect |
| Buddy/depth review | Ordinary bounded native child with complete assigned canonical review source; reports to architect or its assigned pipeline supervisor within the team |
| Resource/explicit DevOps request | Manager relays team's unchanged technical request/authorization to shared `startup-role-devops` |
| Reminders | `startup-role-pa` receives own scoped cues/manager summary and reports to manager |

Ordinary native pipeline supervisors/buddy/review children count against capacity but have no durable employee inbox/hire authority. Explicitly bind the complete canonical procedure in their native profile or full instructions before work. Generic task descriptions do not create canonical personas.

Intake retains every explicit canonical role request in `requested_roles`; older rows without it behave as `[]`. Ready items fulfill requested specialists before the affected execution starts. Explicit DevOps coordination returns READY, NEEDS_INPUT or NO_ACTION; assessment alone authorizes no provisioning. Existing complete team members fulfill their own requested role; external specialist capacity goes through manager. A team has immutable membership; use new intake/team assignment when new scope requires one.

The architect preserves required buddy review, per-kind QA and bounded architectural APPROVE/scoped REDO gates. Only manager lands/accepts final work, after independent evidence. Binding/activation retries preserve identities and pending work; missing source or capacity remains an explicit blocker.
