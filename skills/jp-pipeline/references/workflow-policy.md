# Workflow policy

This is the authority for workflow scope, task crew and review inheritance. Resolve it through the installed `jp-pipeline` skill's `references/workflow-policy.md`, or `$JP_SKILLS_REPO/skills/jp-pipeline/references/workflow-policy.md`. A sibling-relative `../jp-pipeline` path is not reliable when skills are independently symlinked.

## Scope and crew

`jp-startup` manages an open-ended queue; `jp-dark-factory` runs one fixed queue; `jp-pipeline` delivers one task; `jp-hotfix` fixes a small bug in place. A broader workflow may delegate to a narrower one, but none requires Startup or a particular terminal. Factory follow-ups remain outside its frozen queue.

Coordination is executable, not a prompt-maintained ledger: use the host's shared coordinator for admission, reservations, completion, role authority and per-change review state. A status table may summarize receipts but cannot authorize or replace those transitions. Reserve before dispatch and settle only from the correlated real result; an uncertain result stays unresolved until reconciled. If the host cannot carry the same coordinator state and identity through a nested run, stop that run and report the missing capability rather than treating a brief or outcome block as a coordinator.

### Bounded host

If the current OMP session lacks the bounded tools, resolve `JP_SKILLS_REPO` to the absolute installed repository path, then launch a fresh interactive root yourself using a terminal/PTY:

```sh
omp --no-extensions --extension="$JP_SKILLS_REPO/extensions/startup/bounded-entry.ts" --cwd="$PWD" "$BRIEF"
```

Set `BRIEF` in the launching process to the original task, requested skill, all non-secret settings and decisions, current checkout, and a request to continue in this host and return its outcome. Preserve the user's verification and approval requirements; transmit secrets only through an approved secure channel, never in the brief or command. Carry through explicitly selected model and approval settings without weakening them. Forward questions and results between the human and this root. If an interactive PTY or secure channel required by the task is unavailable, report the concrete blocker. Inside the new root, require `bounded_begin` to be available; if it is not, stop rather than recursively launching another root. This does not select a Startup or modify the default profile.

For a standalone Claude Code root, launch `bun "$JP_SKILLS_REPO/extensions/startup/claude-bounded-entry.ts" "$BRIEF"` instead. Its process-local MCP server exposes `mcp__bounded__bounded_*`; load the tools with ToolSearch. Call `bounded_begin`, then reserve each foreground `Agent` with `bounded_plan`, `bounded_prepare`, or `bounded_review` and include the returned marker in its prompt. Read the correlated result with `bounded_result`. Background or missing receipts remain uncertain. The root owns nested scopes and review; a Claude subagent cannot control the parent authority. Do not disable hooks or replace the launcher's session, MCP or settings.

In OMP, the root calls `bounded_begin` with `workflow` (`factory`, `pipeline`, or `hotfix`), the complete `itemIds`, `reviewLimit`, and `landing` (`mode`, `target`, and optional `allowedChildTargets`). Keep its `scopeId`; the factory queue and landing targets are frozen. Use `bounded_nest` with the parent scope and inherited item IDs for narrower work; never begin a new standalone scope for a nested run. Read `bounded_status` for authoritative state. The bounded `task` tool reserves and dispatches one real native task per call using `scopeId`, `itemId`, `assignmentKey`, `context`, and a single-element `tasks` array. Use its `role` or `review` fields for corresponding receipts. Reconcile an uncertain native assignment with `bounded_reconcile`, not a duplicate dispatch. Use `bounded_complete` only with actual PR, worktree and head evidence. For a hotfix, call `bounded_request_approval` with scope, worktree and exact head, then obtain the human's one-word `go` as actual interactive/RPC input; a model assertion is not approval.

For an OMP factory requiring planning, omit `dependencies` from `bounded_begin`, then dispatch the Planner via `task` with `planner: true`, the factory `scopeId`, any frozen item ID as `itemId` anchor, a unique `assignmentKey`, `context`, and one planner in `tasks`. Its correlated terminal JSON must contain `dependencies` and `targets` maps for every frozen item. The host validates and freezes these maps; read `bounded_status` until `graphFrozen` is true before ticket dispatch. Preserve an uncertain planner reservation for reconciliation rather than relaunching. `bounded_ready` records a QA-backed ready PR for dependency scheduling without marking the item finally complete, allowing cross-queue review before merges. Reserving another assignment for that item invalidates readiness; publish it again only after all assignments settle and the current PR and matching-head role evidence pass. After a head changes, obtain fresh matching dev and QA evidence.

Tern and Herdr remain optional. An OMP root creates a nested scope, then requests `bounded_launch` for that scope; the child attaches with `bounded_attach` and never receives a token in its prompt. Inherited role assignments return authenticated evidence to the parent; inherited review remains parent-owned. The child hands ready PRs back with `bounded_finish({scopeId,items:[{itemId,worktree,head,prNumber},...]})`; the parent verifies scope, PRs and role readiness before marking them ready. A native task child cannot act as its parent owner. For an explicitly selected Startup, the manager first fixes each item's review limit and target with `startup_workflow_limit`, then uses `startup_workflow_factory_start` for a fixed queue, or an assigned employee uses `startup_workflow_start` for a pipeline or hotfix. The launched child attaches to the Startup owner's canonical scope; reviews and landing stay with Startup. Follow the tool contracts in `$JP_SKILLS_REPO/extensions/startup/README.md`. If inherited receipts cannot be obtained, report the concrete blocker rather than beginning an independent scope. Preserve `STARTUP_MODE=off`.

For a factory or pipeline, the initiating coordinator arranges a task crew: a manager/coordinator, architect, one or more developers and QA. The coordinator authorizes dispatch and maintains runtime state; the manager handles questions and publication; the architect owns technical decomposition and coordination; developers implement; QA independently proves the result. Add PA or DevOps only when needed. A factory's crew coordinates the fixed queue and ticket pipeline crews perform ticket work. In a nested workflow, reuse already assigned, available crew members when their authority and scope cover the work; otherwise reserve the missing roles. Do not duplicate a role merely because a nested skill starts. Startup's admitted employees and their runtime authority stay under Startup's own procedures; local task helpers are not Startup employees. A hotfix is a narrow path and does not spawn the full crew.

## Review budget and inheritance

A review round is one completed code-review pass with its verdict; reviewer angles, batches and debate inside that pass are not additional rounds. Reserve each review against the shared coordinator's per-change state and settle it from the correlated verdict and reviewed head. Count all rounds touching the same change across nested workflows against that one state; a nested workflow never resets or adds a budget. An incomplete attempt without a verdict is not credited and must be reconciled before the gate advances.

For Startup code changes, the manager or owning architect uses `startup_workflow_review` and the admitted reviewer's authenticated result; follow the reserve, result and settle protocol in `$JP_SKILLS_REPO/extensions/startup/README.md`. Code landing requires the matching completed approval reservation and reviewed head in decision evidence. Independently confirm the actual git head matches that reviewed head; the coordinator does not read git. Non-code work keeps Startup's existing QA gate.

The outer scope sets the cap, bounded by the nested workflow's own cap when it independently reviews that change: hotfix one; pipeline at most two; dark-factory at most three; Startup's manager chooses a cap at most three and passes it down. A stricter inherited cap always wins. Select the cap before review, do at least one applicable review, and stop on the first APPROVE; there is no minimum number of repeat rounds. A factory may defer ticket pipeline reviews to cross-queue review; each round consumes one for each change it covers. QA, planning debates and the owning Startup architect's architecture gate are distinct from code-review rounds, not a way to relabel another code-review pass.

Fix and verify actionable must-fixes. If a further review fits the remaining budget, review the updated change; otherwise report the post-review fix as unreviewed and stop if an unresolved finding or required approval remains. Never manufacture an APPROVE for an unreviewed revision. A BLOCK escalates; a genuinely false positive requires an evidenced disposition. Any simplification after the final review is explicitly reported as unreviewed and verified under the caller's gate. Review skills must honor the inherited cap, not demand an extra pass.
