# Local disk maintenance

## Read-only triage before cleanup

1. Resolve this host with `hostname`, `uname`, and `df`; do not infer it from user memory or redirect to a known remote server. On macOS inspect `df -h /System/Volumes/Data` rather than reporting only the small read-only system volume. Use the timestamped `storage/server-maintenance/ledger/local.json` record and append actual changes with the private-storage helper; sync before reading and execute the shared post-run hook before finishing. Legacy `servers/local*.md` files are migration sources only.
2. For an existing scheduled check, inspect its current CLI job state and retrieve the latest completed report. Check `hermes cron runs --help` before querying execution history; current syntax uses the positional job ID (`hermes cron runs <job-id> --limit 2`), not `--job-id`. Label the completed report as historical and sample `df` again for the answer; active scheduling does not mean a cleanup is currently executing.
For user-authorized unattended cleanup jobs, separate execution authority from retention questions: explicitly authorize only verified safe categories, load the maintenance skill directly, prioritize measured reclaimable candidates, and reserve bounded time for cleanup and verification instead of repeating an exhaustive census. Require a non-silent measured no-op report when nothing qualifies; silence is not evidence of healthy cleanup. Avoid retrying identical ineffective GC without changed eligibility. Preserve all existing safety gates. Read back the exact updated job and distinguish accepted/skipped manual fires from completed cleanup; do not launch a competing pass when the scheduler says one is already running.

3. Bound disk scans by directory and time. Start with `du -sk` on development roots, package stores/caches, agent homes, the canonical skill home, Downloads, and known container storage. Drill into the largest roots with `du -k -d 1`. Use small concurrent batches with per-directory timeouts rather than a whole-home scan, which can stall on protected or cloud-backed Library folders. Apply repository-discovery directory/time budgets independently per root: a cumulative cap must not cause subsequent roots to be silently skipped. Record exact depth-pruned paths and retry capped roots with appropriate build/dependency exclusions.
4. Checkpoint each batch into a compact audit artifact before optional tool probes. Retain successful sizes when another scan times out or fails; label permission-limited `du` totals as partial/lower bounds instead of complete inventories. Give Docker daemon probes their own bounded timeouts and run independent package/store checks separately: `docker context inspect` can succeed while `docker system df` and `docker version` hang. Do not restart an engine merely to finish its inventory. Do not change privacy permissions merely to finish a size report.
5. Inspect large top-level files as well as subdirectories, using metadata rather than private contents. Agent history databases and installer images can account for space that a directory-only listing does not explain. Keep parent totals separate from their children to avoid double-counting.
6. Rank candidates as rebuildable cache, reference/idle checks required, or persistent data requiring explicit retention decisions. An `old`, `tmp`, `cache`, or `reclaimable` label is not deletion authorization. Report the recommended first pass and what remains unverified before requesting approval.

## Candidate-specific checks

- Confirm the Docker engine belongs to this host before treating its usage as local: run `docker context show` and inspect the endpoint with `docker context inspect --format '{{json .Endpoints.docker.Host}}'`, accounting for explicit endpoint overrides too. Then use `docker system df` to separate build cache, images, containers, and volumes. Provider-reported reclaimable bytes are estimates inside the engine/VM, not guaranteed immediate macOS recovery. Preserve volumes and in-use resources; never substitute `docker system prune --volumes` for a build-cache-only approval.
- For authorized Docker build-cache collection, inspect `docker buildx du --format json` and the installed prune help first. Prefer cache-only age-filtered collection such as `docker buildx prune --builder <verified-local-builder> --filter until=24h --force`, without `--all`, after checking for active builders/qualification drivers. Snapshot exact image/container/volume IDs immediately before and after, then read back cache usage. Docker inventories can change concurrently; never attribute other actors' image/container/volume removals or the full host free-space increase to cache GC. A successful age-filtered prune can report `Total: 0B` while system df still lists reclaimable cache; record the unchanged cache IDs/usage and do not broaden to `--all` or remove the age filter merely to chase that estimate. Keep engine-reported bytes distinct from immediate and final APFS readings, including delayed VM-space return. Compare successive JSON cache inventories by ID and stable size/reference fields in code, sorting records and parent lists; raw output equality is unreliable because row order and relative LastUsedAt strings can change without any cache mutation. Do not repeat an ineffective prune solely because those display fields changed.
- Inventory each pnpm store version separately and confirm the selected store with `pnpm store path`; pruning one active version does not establish that another version is unused. Inspect npm caches separately too: `_npx` contains runnable tool installations, so check Node-hosted processes and handles rather than only looking for an executable named npm or npx. Use the package manager's supported cache operations after authorization and idle checks.
- Assess SQLite compaction potential without reading conversation contents: open via a read-only URI and inspect `PRAGMA page_size`, `page_count`, and `freelist_count`; calculate free-page bytes in code. A large history database with negligible freelist space is not a useful compaction candidate. Do not delete its data or run VACUUM against an active application merely because it is large.

## Worktrees and build outputs
- Discover repositories and linked worktrees with `git worktree list --porcelain`, deduplicating by absolute common Git directory. Include nested `.claude/worktrees`, `.worktrees`, canonical skill worktrees, and Codex roots. Broken leaf gitdir pointers require parent-side inspection; preserve when status cannot be established.
- Keep the primary checkout or absolute common Git directory as the stable registry handle after deduplicating repositories. Discovery can start inside a disposable linked worktree; never use that leaf as the post-removal verification cwd. Verify removal with `git --git-dir <absolute-common-dir> worktree list --porcelain` if the discovery checkout was removed.
- Before removing a worktree, require successful clean status including all untracked files, GitHub-confirmed MERGED state with non-null mergedAt, and exact local HEAD equality to the PR head SHA. Preserve mismatches, detached or locked trees, open/closed-unmerged PRs, and unknown states. Resolve the current branch from the fresh worktree registry rather than its directory name: agents can reuse an old ticket-named directory for a different branch and PR.
- Inspect ignored files too: generated dependencies and build output can be discarded, but ignored environment files, QA evidence, slides, or other non-build files must be preserved. A clean Git status alone does not prove a tree disposable.
- Treat an ignored Python virtualenv as disposable dependencies only after inspecting its layout and files. Compare files against installed packages' `.dist-info/RECORD` inventories plus known environment-manager bootstrap/activation files and generated bytecode; preserve unknown files. Packaged `share/doc` or manpages are dependencies when RECORD-covered, not user documents. Do not execute code from the environment during inspection. Keep the usual merged-PR, clean-status, ignored-content and idle gates for removing its enclosing worktree.
- Keep every checkout's ignored inventory compact, including linked or detached copies of a primary checkout: record exact nested `.worktrees/` and `.claude/worktrees/` roots and immediate leaf names without recursively expanding them; apply this guard when the ignored inventory entry itself is a worktree root, not just when encountered as a child during recursion. Audit registered linked checkouts separately. Preserve unregistered copied trees as unclassified content, not disposable registrations. While enumerating preserved custom roots, prune nested dependency/build directories (`node_modules`, `.venv`, conventional Cargo output) from file-level evidence, but retain their exact root names. This prevents duplicate dependency inventories from making the cleanup audit itself consume substantial disk space; never omit custom scripts, environment files, or QA evidence.
- Collect tracked/untracked cleanliness separately with `git status --porcelain=v1 --untracked-files=all`; inventory ignored roots with `git status --porcelain=v1 --ignored --untracked-files=normal -z`. Combining ignored inventory with `--untracked-files=all` expands every dependency/build file and can produce tens of megabytes of noise. Recurse preserved non-build roots separately to record exact evidence/script names, and print only bounded summaries.
- Check live processes and handles using both global `lsof -nP -Fpcfn` (including deleted files and cwd) and `lsof +D <candidate>`. Treat command errors/timeouts as an unsafe idle check. Recheck status and HEAD immediately before non-forced `git worktree remove`; verify both path absence and removal from the parent registry. Never kill a holder just to reclaim space without authorization.
- Remove Rust targets only when they are confirmed ignored, contain no tracked files, have no handles or active checkout cwd, and no build/analyzer process can race the deletion. Preserve source and unmerged worktrees even if their idle rebuildable target is removed.
- Discover other framework outputs afresh rather than carrying forward only the previous run's Rust target list. An ignored Next.js `.next/` can be removed as rebuildable output after confirming the owning package declares Next, conventional generated contents, no tracked or nonignored files inside, a stable recursive metadata/size snapshot and 30-minute cooldown, no build/server driver, and successful fresh global checkout-wide plus recursive output handle checks. Do not follow symlinks out of the output or run builds to verify cleanup. Compare checkout tracked/untracked status before and after; verify output absence and no deleted-file holders. Preserve source, `.env`, data and public assets.
- Discover custom Next output names from `next.config.*` `distDir` and test-driver environment assignments (for example `.next-e2e`), not only directories literally named `.next`. For mixed dev output, qualify an exact generated chunk subtree by Turbopack markers and paired valid v3 sourcemaps; preserve sibling logs, lockfiles, manifests and runtime dependency links. Validate indexed v3 sourcemaps recursively through each section's offset and embedded map, as well as ordinary maps with sources/mappings; a missing top-level mappings field alone does not make an indexed map invalid. Preserve unpaired or invalid files and remove only individually qualified pairs when the full subtree is not classified. Never follow sibling links into dependencies: record each link's lstat metadata and target and verify it unchanged. Apply the same ignored/no-tracked/nonignored, cooldown, stable metadata, process and checkout-wide/global/recursive handle gates; state that the next preview/test must regenerate the deleted chunks.
- Qualify Turborepo `.turbo/cache` as generated task-result output, not installed tools: require package build scripts and `turbo.json` provenance, exact hash-named `.tar.zst`/`-meta.json`/`-manifest.json` triples, matching metadata hash, valid manifest schema and Zstandard archive contents confined to declared build/cache outputs and task logs. Compare archive files against manifest entries; archives may also contain parent directory entries omitted from the manifest, which are valid only when they are actual directory members and ancestors of listed outputs. Reject archive links/unknown members. Apply ignored/no-tracked/nonignored, stable recursive metadata, >30-minute cooldown, fresh builder/driver and global checkout-wide/recursive cache holder gates. Preserve checkout changes and registry; verify exact cache absence and no deleted holders. Removing local task results causes later tasks to rebuild or refetch remote cache, not deletion of source or installed dependencies.
- Reassess substantial unchanged outputs as well as new/growing ones. A prior measurement or preservation decision is not permanent classification: inspect unresolved generated output using fresh provenance and safety gates rather than treating no size growth as proof that nothing can be pruned.
- Qualify OpenNext `.open-next/` deployment output separately from source or live runtime state. Require the owning package's declared OpenNext adapter/build script, exact conventional output layout and file classification, consistent BUILD_IDs across bundled Next manifests/assets, all files ignored with no tracked/nonignored entries, no symlinks or unclassified evidence/environment data, stable recursive metadata, >30-minute cooldown, and fresh builder/global-checkout/recursive-output handle gates. Preserve unknown/copied custom assets; remove only a fully classified generated subtree. Verify absence, unchanged Git status and protected sibling metadata, and no deleted-file holders. State that Cloudflare preview/deployment from this checkout needs regeneration; do not rebuild merely to verify removal.
- Discover Nuxt `.output/` roots alongside Next.js output; Nuxt static generation may place hashed compiler assets beneath `.output/public/static/_nuxt/` rather than a top-level `_nuxt/`. Establish provenance from the owning package's `nuxt generate` script and `nitro.json` framework/preset, then classify exact files before pruning. Preserve nonidentical copied static assets, route HTML, custom state and evidence when provenance is incomplete; prefer narrowly verified generated-asset subtrees rather than inferring that every `.output/` sibling is disposable. Apply ignored/no-tracked/nonignored-files, stable recursive metadata, 30-minute cooldown, process-driver and checkout-wide/global/recursive handle gates; verify unchanged Git status, protected siblings and no deleted holders. State that an old static build needs regeneration before preview after its assets are removed.
- Do not clear a whole Swift `.build/` solely because SwiftPM owns its name: it can include custom `qa/` evidence and app bundles alongside compiler output. Classify subdirectories separately under the same provenance, ignored-content, cooldown and idle gates. Prefer narrowly inspected compiler-only candidates such as `<triple>/{debug,release}/ModuleCache`, `<triple>/debug/index`, and `apple/{CompilationCache,Intermediates,ModuleCache}.noindex`; retain binaries, `.dSYM`, QA/app bundles, dependency checkouts and `apple/Products`. Establish ownership from `Package.swift`, inspect candidate contents rather than names alone, check Swift/Clang/Xcode builders and checkout-wide cwd/handles, and verify protected bundle/evidence paths plus unchanged Git status after deletion. `apple/SDKStatCaches.noindex` is another narrow candidate only when its contents are regular generated `.sdkstatcache` files with the `STAT` header; require the same provenance, ignored/no-tracked/nonignored-files, stable metadata, cooldown and idle gates, and preserve all sibling products and evidence. Do not rebuild merely to verify cleanup.
- Qualify explicit Swift/Clang module-cache roots outside SwiftPM separately when a surviving build driver names the exact `-module-cache-path` and surviving source files prove ownership; do not require `Package.swift` for a direct `swiftc` driver. Require only regular compiled `.swiftmodule` files with the Swift module magic, `.pcm` Mach-O `MH_OBJECT` files with `__CLANG/__clangast` sections, `modules.idx` with `BCGI` magic and an empty `modules.timestamp`; preserve unknown contents and all app/object/evidence siblings. Apply ignored/no-tracked/nonignored, stable recursive metadata, >30-minute cooldown, fresh compiler/driver/global-checkout/recursive holder gates, then verify cache absence and every protected non-directory sibling's metadata plus Git status/registry unchanged. The next build regenerates the module cache; do not rebuild merely to verify removal.
- When Swift caches are already absent but mixed `.build/` products must be retained, qualify individual Swift `.o` files rather than clearing enclosing directories. Require each exact object path in its target's `output-file-map.json`, a surviving source in the owning package or declared dependency checkout, and a Mach-O header identifying `MH_OBJECT` (not an executable or dylib). Apply ignored/no-tracked/nonignored-files, >30-minute cooldown, stable full-tree metadata, fresh compiler/driver plus global checkout-wide and recursive lane handle gates. Preserve maps, generated headers/source, app/QA bundles, binaries, dSYM and dependency checkouts; verify every non-directory sibling's metadata and Git status unchanged, object absence and no deleted holders. The next build must regenerate objects; do not rebuild to verify removal.
- Treat active build-driver scripts and containerized qualification/build commands as potential artifact users even between compiler invocations. An idle cargo/rustc process snapshot does not prove safety while a long-running build driver can launch the next build; preserve its checkout artifacts and defer broad artifact pruning until it finishes.
- During unattended maintenance, defer build directories modified within the last 30 minutes or whose size/content changes during the audit; an idle process/handle snapshot does not establish that an agent has finished using a newly active checkout. This conservative cooldown supplements, never replaces, the process and handle gates.
- Treat a recursive deletion error such as `Directory not empty` as a possible concurrent-build race, not permission to retry or force. Stop further artifact pruning immediately, preserve remaining/recreated output, record the partial mutation and fresh process/handle evidence, and report the incomplete removal separately from successfully removed paths.
- On macOS use `ps -ww -axo pid=,comm=` (with comm as the final field) for executable detection, and collect `ps -ww -axo pid=,args=` separately for arguments; cross-check process names from global lsof. Default `ps`, and even `ps -ww` when comm is followed by args, truncates the comm field (for example `/Users/jarredpar`), so basename matching can silently miss cargo/rustc/analyzers. Separate snapshots can contain different PID sets: re-query an unmatched PID with `ps -ww -p <pid> -o comm=`; accept a confirmed exited process, but defer cleanup if a live executable cannot be resolved. Never silently drop unmatched live processes or crash and then skip the idle gate. If any build starts or a removed target regenerates, stop further artifact cleanup, preserve the rebuilt path, and report it.
- Inspect a bounded number of levels below each Cargo target for nested conventional output such as `target/client/rust/debug`; absence of top-level `debug/` or `release/` does not establish that no rebuildable artifacts remain. Apply the same manifest, ignored/no-tracked-files, content, process, cwd and handle gates to each nested candidate.
- Inspect target contents rather than assuming everything beneath `target/` is disposable. First establish that the path belongs to a Cargo build (manifest/config plus conventional output); an unrelated `data/target` can hold database restoration receipts or private state, not build artifacts. Inventory names without opening private content. Custom subdirectories can contain ignored proof scripts or QA evidence; preserve exact non-build paths and clean only separately verified conventional build subdirectories. Analyzer `flycheckN/stdout` and `stderr` are generated logs, but still require idle checks.
- Discover redirected Cargo outputs by their conventional `debug`/`release` lanes with `.fingerprint`, `deps`, and `build` plus a parent `CACHEDIR.TAG`, not only directories literally named `target`; ignored SDK qualification trees can use names such as `cohort-target` and contain a second target-triple lane. Treat this signature as discovery only, never deletion approval. For a redirected Cargo target with no adjacent `Cargo.toml`, establish ownership using the owning package manifest, generated package `.d` dep-info naming the exact output lane and matching source modules, fingerprints/cache tags, and the task ledger or build configuration. An absent adjacent manifest alone is not a permanent blocker, but a Cargo-shaped directory name alone is not provenance. Apply the same ignored/no-tracked-files, conventional-content, cooldown, stable-snapshot, builder/driver and handle gates to each lane; preserve surrounding task ledgers, custom scripts and evidence. Do not run Cargo or rebuild merely to identify ownership.
- Inventory macOS simulator/runtime storage without double-counting mounted images: use `du -x` for `/Library/Developer` and inspect backing assets separately from `/Library/Developer/CoreSimulator/Volumes`. A mounted runtime's expanded size is not additional reclaimable host storage. If default `xcrun simctl` is unavailable, a command-local `DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer` can select an existing Xcode without changing global configuration. An unaccepted Xcode license blocks simulator qualification; never accept it, invoke sudo, or manually delete runtime assets during unattended cleanup. Preserve and report the blocker.
- Do not prune Docker volumes, databases, archives, user documents, browser profiles, or other persistent state on an unused/reclaimable label alone. Leave questions in the final report of unattended runs without blocking safe cleanup.
- Interpret recursive `lsof` using output as well as exit status: status 1 can accompany real matching handles. Only a completed recursive scan with no output, no stderr and status 0/1 is an idle result; never treat status 1 alone as proof of no holders. Filter raw global/recursive handle records before printing, but retain candidate-specific evidence in the audit manifest.
- Preserve exact ignored-path names in the audit manifest, including for trees kept without deletion; a generic keep reason is insufficient evidence if another agent later removes the tree. For protected browser profiles, record the exact profile root, its immediate leaf names and the preservation decision instead of expanding thousands of internal cache/database files in every copied checkout; keep surrounding QA scripts and evidence individually named.
- Distinguish unreferenced-package garbage collection from clearing an entire download/store cache. For pnpm, confirm `pnpm store path`, inspect `pnpm help store`, and use `pnpm store prune` only after idle checks; retain the manager's package count and before/after store sizes. Do not infer that pruning the active store also cleaned older store versions, or that a footprint reduction equals reclaimed APFS space. Inspect the actual prune output: implementations that report checking registered projects for global virtual-store usage and "No unused packages found" have not established that every package in the ordinary content-addressable store is referenced. Report the command's scope and unchanged measured size rather than claiming the entire store was exhaustively pruned.
- Qualify pnpm registry metadata separately from its package store and runnable `dlx` cache. Inspect installed `pnpm cache --help`, `pnpm cache delete --help`, `pnpm cache path` and manager inventories; use the supported metadata-delete command only after stable metadata/cooldown and fresh process/global/recursive-holder gates. Registry metadata can be JSON or a framed `.jsonl` format with an ASCII `pnpm-meta-v1 <metadata-bytes> <index-bytes>\n` or `pacquet-meta-v1` header, followed by those exact-length JSON blocks and concatenated version JSON objects. Parse the ASCII lengths, validate both blocks and decode the remaining objects; do not assume binary integer framing or ordinary JSON Lines. A `'*'` delete pattern may omit scoped names; independently qualified `'@*/*'` can select scoped metadata in the manager's active layout without touching other versions or runnable tools. Snapshot runnable `dlx` and lockfile bookkeeping separately and verify unchanged after eviction. Read back exact removed paths, remaining manager inventory and per-version footprints: the CLI version does not establish which `vN` cache layout it selects, and `'*'` can leave scoped packages or other version roots. Never broaden to raw deletion or execute another cached manager just to chase untouched bytes. Label this metadata eviction, not unreferenced package-store GC; future installs may refetch registry metadata.
- Qualify Go's generated build cache with `go env GOCACHE`, its README and installed `go help clean`; use only `go clean -cache` after stable recursive metadata, >30-minute cooldown, no symlinks/unclassified files and fresh compiler/driver/global/recursive-handle gates. Preserve module download caches and fuzz inputs unless separately authorized. Go can store cached executables in `<two-hex>/<64-hex>-d/<executable>` directories, not just flat `-a`/`-d` files: confirm this layout against installed `cmd/go/internal/cache/cache.go` PutExecutable/copyFile and inspect the executable before classification. Verify original artifacts absent, no deleted-file holders and before/after `du` and `df`; the next Go build/tool run may recompile.
- Treat `bun pm cache rm` as broader than `bun pm cache`'s printed install-cache path: it can also clear cached bunx tool installations outside that directory. Inspect installed implementation/help and locate every affected root before use; independently inventory and qualify bunx roots with runtime/driver, metadata/cooldown and global/recursive holder gates. A missing top-level `bunx-*` entry in the install cache is not proof that no bunx cache exists. Preserve live runnable tools and global installed packages; do not claim bytes for secondary caches without before/after measurements. Run `bun pm cache` from an existing package or an owned minimal scratch package because it fails in a home directory without package.json; prefer owned scratch to avoid automatically loading a user project's `.env`, and never initialize or alter a user project just for the probe. For installed Bun 1.3.x, inspect the matching release's `src/cli/package_manager_command.zig` (not `pm_command.zig`): cache eviction also enumerates `platformTempDir()` and removes every immediate `bunx-<uid>-*` root, including scoped-package containers. Snapshot that exact prefix inventory and gate every affected root; unrelated temp entries remain out of scope. Use `du` for per-path allocated footprint rather than summing raw `st_blocks`, which can count hardlinks repeatedly. Independently measured cache roots may also share hardlinks: do not present their sum as unique storage reclaimed. When verifying surviving hardlinked global packages, compare paths, inode, mode, size, mtime and symlink targets; unlinking a cache hardlink can legitimately change surviving inode ctime/nlink without changing installed contents.
- For authorized npm download-cache eviction, inspect `npm help cache` and the installed implementation/config flattening to verify that `npm cache clean --force` targets only `<cache>/_cacache`, separately from `<cache>/_npx`. Confirm the configured cache path and fresh stable metadata plus global/recursive no-holder gates. Long-running `npm exec` MCP wrappers are not themselves evidence of an active package download: qualify their exact command and preserve the runnable `_npx` tree with a before/after recursive metadata check. Defer on actual installers/cache writers or uncertain processes. Label this whole download-cache eviction, not unreferenced GC; future installs may redownload packages. The documented npm `--force` acknowledges cache eviction only; never use it to bypass ownership, permissions or worktree gates.
- Qualify cached application-update ZIPs individually: require updater metadata SHA-512 equality, embedded app Info.plist identifier/version/build matching the installed app, regular nonsymlink files, stable metadata and >30-minute cooldown, no live app/updater, and successful fresh global/recursive handle gates. Delete only the qualified ZIPs, preserving update metadata and unrelated contents. Verify exact ZIP absence, protected metadata unchanged and no deleted-file holders; keep live-app updater downloads deferred even when the installed version matches.
- Qualify node-gyp development-header caches separately from installed Node runtimes and native modules: inspect installed `node-gyp --help` and `lib/remove.js`, confirm exact `--devdir` and `node-gyp list` inventory, numeric installVersion markers, matching node_version.h version macros, and regular include/node `.h`/`.gypi` trees without unknown files or links. Require stable recursive metadata, >30-minute cooldown and fresh compiler/native-build/install-driver plus global/recursive no-holder gates. Use supported `node-gyp remove <exact-version> --devdir <verified-cache>` only; read back each path, manager inventory and deleted-file handles. This evicts downloadable development headers, not installed Node, native modules or environments; future native builds may download headers again.
- Prune package caches with their package-manager command rather than raw recursive deletion. If pruning fails on root-owned entries, preserve the blocked entries and report the permission issue; do not escalate, chown, or force removal during unattended maintenance. Cache files can be hardlinked into installed environments, so do not chmod cached files to bypass a failure. Record partial cache-size changes separately from actual df free-space changes.
- Save a compact manifest and operation log. Verify `df` after deletion and global handles against removed paths. Report the actual free-space delta, not the sum of `du` sizes: APFS clones/snapshots and concurrent writes can make these differ substantially. On busy hosts sample both run-start and immediately-pre-deletion baselines; distinguish the net run delta from the deletion-window delta and never attribute concurrent changes solely to cleanup.
- Delete only scratch created by this run after preserving its audit manifest. Do not touch other agents' scratch or another Hermes profile.
